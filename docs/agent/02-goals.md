# 02 · 目标与验收标准

## 1. 产品目标

| ID | 目标 | 衡量方式 | 目标值 |
|---|---|---|---|
| G-01 | 新用户能独立完成一次核心闭环 | 可用性测试：录入 → 分析 → 生成 → 保存 | 3 分钟内完成，无需帮助 |
| G-02 | 生成结果可用于练习 | 人工抽检 20 组生成结果 | ≥ 80% 题目可作答、答案基本正确 |
| G-03 | 用户知道下一步复习什么（P1） | 学习概览页能说出 1 个薄弱知识点 | 3/3 测试用户能说出 |

## 4. 学习目标

这是实验室考核，不只是交付产品。两人都应能讲清：

- 前端：为什么这样设计信息架构、如何处理 AI 长请求/流式、如何做错误态与空状态。
- 后端：为什么选 FastAPI、如何保证 LLM 输出结构化、DeepSeek 文本+图片提取怎么接、SQLite/MySQL 差异怎么处理、如何防止密钥泄露。
- 共同：如何做技术选型、如何拆任务、如何做 Code Review、如何保证演示稳定。

## 5. 验收标准

### 5.1 P0 功能验收（逐项打勾）

- [ ] 注册/登录/退出可用；未登录访问受保护页面会跳转登录。
- [ ] 文本录入题干必填、长度限制、学科必选；电脑支持粘贴/拖入；提交后有明确反馈。
- [ ] 电脑端可粘贴/拖入图片；手机端可选拍照或相册；图片预览/删除/重试正常；上传前支持裁剪并重置。
- [ ] 上传裁剪后的图片，DeepSeek `deepseek-flash` 能提取 1..N 道题目文本（公式 LaTeX），按 ① ② ③ … 单独显示；用户可逐条编辑/确认；当前阶段不提取附图；失败可重试/改文本。
- [ ] 三种题型（选择/填空/解答）可创建、显示、编辑；工具栏至少支持 LaTeX 模板/编号/基础排版；KaTeX 错误不丢内容。
- [ ] AI 分析返回知识点（3–5 个）、题型、难度、错误原因；字段缺失时有兜底；分析可编辑写回。
- [ ] 生成恰好 3 道题；每题有题干、答案、解析；JSON 解析失败会重试或报错。
- [ ] 生成的题不是原题复制；不依赖“如图”但系统无图；公式可渲染。
- [ ] 错题列表分页、按学科/标签筛选、关键词搜索可用；空状态正常。
- [ ] 详情页能看到原题、分析、3 道生成题；可编辑/删除。
- [ ] 练习模式可作答、计时、查看答案、自评；记录写入数据库（P0）。
- [ ] 任务中心可看列表/状态/失败重试/草稿行；草稿服务端 + localStorage 双写可恢复。
- [ ] 刷新页面不丢登录态；401 自动跳登录；重复点击不会创建重复数据。
- [ ] 部署地址可访问；演示账号有种子数据；API 失败有兜底。
- [ ] 学习概览（P1）：数字与数据库一致；薄弱知识点可解释。

### 5.2 非功能验收

- [ ] 密钥只在 `.env`/服务器环境变量；仓库无密钥。
- [ ] 上传文件类型/大小校验（JPEG/PNG/WebP；前端压缩到 ≤5MB/2000px；服务端接受 ≤10MB 再压）；AI 内容渲染做 XSS 清洗。
- [ ] 图片提取失败/超时不丢用户已输入的文本；可退回文本录入。
- [ ] CORS 只允许前端域名；错误响应不泄露堆栈。
- [ ] SQLite 开启 WAL；MySQL 使用 `utf8mb4`；迁移脚本可重复执行。
- [ ] 日志包含 request_id；AI 调用记录模型、耗时、状态、token。
- [ ] 主流程在 Chrome/Edge 最新版通过；1366×768 和 1920×1080 投影分辨率正常。
- [ ] 断网/超时/额度不足时，页面有可理解的提示，不白屏。

### 5.3 演示验收

- [ ] 演示脚本 3 分钟内走完：登录 → 录入（文本或图片）→ 提取/分析 → 编辑/保存 → 任务中心 → 练习 → 错题本；统计可选（P1）。
- [ ] 准备 2 个账号、≥10 道大学理科种子错题、≥20 条练习记录；至少 3 道含图/公式题用于图片提取展示。
- [ ] 准备 API 失败兜底：预生成结果/缓存/录屏。
- [ ] PPT 7 分钟内；两人都参与；能回答“为什么不用 SpringBoot”“如何保证生成质量”“创新点是什么”。

- 生成题可用率/答案正确率（抽检）。
- 测试用户满意度（3–5 人，简单问卷）。
- 演示成功率（3/3）。

## 7. Definition of Done（单个任务）

一个任务只有满足以下条件才算 `DONE`：

1. 代码实现并通过本地运行。
2. 有必要的测试（后端 service/API；前端关键组件/E2E）。
3. lint/typecheck/build 通过。
4. 相关文档更新（API/数据模型/页面规范/任务状态）。
5. 另一个人 review 过（至少看一眼 diff；小任务可口头确认）。
6. 在部署环境或至少本地完整流程验证过。
7. 没有把密钥、调试代码、`console.log` 垃圾留在提交里。

## 8. 评审视角：他们大概率会看什么

| 评审关注点 | 我们的应对 |
|---|---|
| 产品是否真的解决一个问题 | 用真实错题演示；讲清“错题 → 同类题 → 掌握度”闭环 |
| AI 是否只是套壳 | 展示结构化输出、校验、重试、质量抽检、成本/延迟数据 |
| 技术选型是否合理 | 讲清 FastAPI 的异步/流式优势；SQLite/MySQL 分工 |
| 两人是否都参与 | 分工表 + commit/PR 记录 + 两人分段答辩 |
| 是否有创新 | 不是“AI 生成题”本身，而是“生成 + 校验 + 练习 + 薄弱点”的闭环 |
| 工程质量 | CI、测试、错误处理、密钥管理、部署 |
| 演示是否稳定 | 种子数据、缓存兜底、录屏备份、反复排练 |
