# 01 · 项目定义

## 1. 背景与问题

学生在日常学习中会产生大量错题，但传统错题整理存在四个痛点：

1. **整理成本高**：抄题、剪贴、分类耗时，难以坚持。
2. **检索困难**：纸质错题本厚重，按知识点/时间查找不便。
3. **只会一道题**：看懂了原题，缺少同类题练习，换个数字或情境又不会。
4. **缺少掌握度反馈**：不知道哪个知识点反复错，复习没有优先级。

现有搜题/题库产品大多解决“这道题怎么做”，而不是“这类题我有没有掌握”。本项目要补的是**从错题到同类题再到掌握度**的闭环。

## 2. 目标用户

**已确认**：大学理科生，数学/物理为主，覆盖高数、线代、概率论与数理统计、大学物理等；有错题整理需求，但不愿花大量时间抄题；电脑上传图片、手机拍照/相册录入。

**主画像**：大二理工科学生，高数/线代/大学物理错题多，不知道怎么找同类题练；希望 3 分钟内完成一次“录入 → 生成 → 保存”。

> Q-001 已确认。当前阶段以大学理科为主（高数/线代/概率论/大学物理），演示数据统一用大学理科题目；通用学段/其他学科作为后续扩展，优先级低，不进入 P0。数据模型保留 `subject` 字符串，不把学段写死成枚举。数据库 schema 由人机负责，本文档只定义产品范围。

## 3. 价值主张

> 一道错题，三道同类题，一个薄弱点闭环。

- **输入轻**：文本粘贴 + 图片识图双入口；电脑上传图片，手机拍照/相册；识图结果可编辑。
- **输出准**：不是泛泛的“类似题”，而是同知识点、同题型、同难度、可作答。
- **可追踪**：练习记录 → 正确率 → 薄弱知识点 → 下一轮练习。
- **不是搜题工具**：我们不给“这道题的答案”，我们给“这类题的练习”。

## 5. 范围

### P0（11.21 前必须完成，11.29 必须稳定演示）

1. **最小登录**：注册、登录、JWT、退出；不做找回密码/邮箱验证。
2. **双入口录入**：电脑粘贴/拖入；手机相册/拍照；两种入口都能进入识别/分析。
3. **AI 预框 + 识图**：两端都先 AI 框定核心题目 → 用户确认/切换候选 → 裁剪 → DeepSeek `deepseek-flash` 识图；结果可编辑。**不做独立 OCR 服务**。
4. **三种题型 + 工具栏（P0 增强）**：选择题、填空题、解答题；LaTeX/编号/表格/插图按时间降级。
5. **AI 分析**：返回 3–5 个知识点、题型、难度、错误原因；结构化 JSON；分析可编辑写回。
6. **生成 3 道相似题**：题干 + 答案 + 解析；服务端校验；失败可重试；单题重新生成 P0 基础版。
7. **错题管理**：列表、详情、编辑、软删除；按学科/标签筛选；关键词搜索。
8. **练习模式（P0）**：逐题作答、计时、查看答案、自评对错、记录。
9. **任务中心 + 草稿**：列表 + 状态 + 失败重试 + 草稿行；草稿服务端 + localStorage 双写。
10. **部署与演示**：可访问地址、种子数据、演示账号、失败兜底。
11. **基础工程**：CI、`.env.example`、数据库迁移、健康检查、日志。

> 图片入口是“P0 增强”：如果 11.21 前进度紧张，演示退回文本录入，但产品设计/接口仍保留图片入口，不能把文本闭环也拖垮。

### P1（P0 稳定后再做，11.21–11.27）

- 学习统计/概览：4 个数字 + 薄弱知识点 + 趋势图。
- 复习模式。
- 错题导出（PDF/图片）。
- 移动端其余页面适配（录入入口已在 P0）。
- token 级 SSE（P0 只做阶段级）。
- 多图/批量上传（如果时间允许）。
- 手动微调/拖拽画框。

### P2（明确不做进本次演示，可作为 PPT 的未来规划）

- 知识图谱可视化。
- 模型训练/微调、强化学习动态优化。
- 复杂个性化推荐算法。
- 社区、分享、教师端、付费、多租户。
- 全学科深度覆盖。
- 独立 OCR / 开源 OCR 兜底。

### 非目标（Non-goals）

- **不做模型训练**：使用预训练 LLM + Prompt + 校验，不在 25 天内训练模型。
- **不做完整知识图谱**：MVP 用“标签 + 学科”表达知识点关系。
- **不做拍照解题/答案搜索**：避免与搜题产品正面竞争，也避免版权和合规风险。
- **不做复杂社交/运营**：没有评论、关注、排行榜。
- **不做完整后台管理**：只做学生端 + 演示所需的最小管理能力（种子数据脚本）。
- **不做独立 OCR**：只走 DeepSeek 多模态识图；OCR 兜底不进入本期演示。

## 9. 与 docx 的关系

`Resource/基于生成式AI的错题整理系统.docx` 是**大创申报书**，描述的是长期愿景；本次是实验室 25 天考核。以下冲突以本项目文档为准：

| docx 内容 | 本项目决策 | 原因 |
|---|---|---|
| SpringBoot + langchain4j | Python 3.13 + FastAPI + OpenAI 兼容 SDK | 已确认技术栈；Python AI 生态更直接 |
| LLM 供应商 | DeepSeek `deepseek-flash`（文本 + 图像） | 官方 API 原生多模态；`deepseek-v4-pro` 不支持图片 |
| 模型训练 / 强化学习动态优化 | 不训练；Prompt + 结构化输出 + 校验 | 25 天不可行，且无高质量数据集 |
| 知识图谱 | 标签 + 学科 + 统计 | MVP 不需要图数据库/图谱推理 |
| 图像识别 OCR | 不做独立 OCR；DeepSeek `deepseek-flash` 多模态识图；结果可编辑；P0 增强 | 多模态直读图文更适合理科；独立 OCR 管线不稳定/成本高 |
| 个性化推荐算法 | 规则 + 统计（薄弱知识点排序） | 可解释、可演示、成本低 |
| 2025–2026 四阶段 | 11.7 / 11.14 / 11.21 / 11.29 | 以实验室通知为准 |
| 生成 3 道相似题 | 保留，作为核心 | 与题目要求一致 |
| 流式消息输出 | P0 阶段级 SSE，P1 token 级 | 兼顾体验与可靠性 |
| 部署 | Docker Compose + nginx | 可复现、易演示 |

> 答辩时如果被问“为什么不用 SpringBoot/langchain4j”，回答要点：技术栈已与实验室确认；Python/FastAPI 在 LLM 接入、异步流式、快速迭代上更适合 25 天交付；docx 是早期申报材料，不是最终实现约束。

## 10. 关键假设

1. 用户愿意粘贴文本，或上传/拍摄图片；识图结果允许手动修正。
2. DeepSeek API 在演示期间可用，文本 + 图像调用成本可控。
3. 大学理科题目包含公式/图形；识图需要保留公式并描述图形，生成题尽量纯文本可作答。
4. 演示环境有稳定网络；否则使用本地缓存/预生成结果兜底。
5. 两人每天能投入 4–6 小时；周末可集中开发。
6. 评审更看重“闭环可用 + 表达清楚”，而不是功能数量。
7. 25 天内不做需要标注数据、训练、复杂算法的工作。
