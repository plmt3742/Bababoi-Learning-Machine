# ADR-004: 图片录入改为「文本提取 + 多题条目」

- 状态：Accepted（2026-11-07 补 §5 落地补充与 §6.1 复审记录，**决策不变**）
- 日期：2026-11-05
- 决策人：霹雳马桶、人机
- 相关任务：BE-014、BE-017、FE-016、FE-021、FE-026
- 相关文档：`docs/agent/05-architecture.md`、`docs/agent/12-backend-alignment.md`、`docs/product/01-prd-lite.md`
- 后端通知：GitHub issue #13

## 1. 背景

原方案是「上传图片 → AI 在图片上检测题目区域（bbox/candidates）→ 用户确认/切换候选 + 移动/缩放 AI 框 → 服务端裁剪 → 识图」。讨论后认为：

- AI 框题不稳定，多题图/整页图容易框错，用户还要理解和操作 bbox。
- 大学理科题目经常一页多题，用户真正需要的是「把图里的题目变成可编辑文本」，而不是「在图上框一个区域」。
- 当前阶段不做附图/图形识别，先把题目文字和公式（LaTeX）提取出来，闭环更短、更可控。
- 用户在上传阶段裁剪图片更直观，能先去掉无关区域，再让模型提取。

## 2. 决策

图片录入流程改为：

```text
选择图片（电脑粘贴/拖入；手机拍照/相册）
  → 用户裁剪图片（可选；可重置为原图）
  → 上传裁剪后的图片
  → AI 提取图片中的题目文本（公式用 LaTeX）
  → 返回 1..N 道题，按 ① ② ③ … 单独呈现为条目
  → 用户逐条确认/编辑（当前阶段只处理文本，不提取附图）
  → 确认后创建 1..N 道错题，进入分析
  → 系统返回答案、解析、知识点、错误原因
  → 用户选择题目条目（选中高亮，可多选，P0 上限 3 道）
  → 点击「生成相似题」→ 为每个选中题目生成 3 道相似题
```

关键约束：

1. **不做 AI bbox / candidates / 框题确认**；`from-image` 不再返回 bbox 或 confidence。
2. **上传阶段支持用户裁剪**；前端裁剪后上传，服务端只做校验/压缩/去 EXIF。
3. **一次识别可返回多题**；每道题是一个独立条目，后续可独立编辑、创建、分析、生成。
4. **当前阶段只提取文本**；题目中的图形/附图不提取，遇到含图题返回 warning，生成题仍要求纯文本可作答。
5. **用户确认后才创建错题**；识别结果不直接入库。
6. **多选生成**：P0 支持选中 1–3 道题目，每道题独立生成 3 道相似题；不要一次对整张图批量生成未确认的题。

## 3. 后果

### 正面

- 交互从「调框」变成「确认文本」，更符合学生「整理错题」的心智。
- 多题图可以一次录入多道题，减少重复上传。
- 前端不需要实现 bbox 高亮/拖拽/缩放，组件更简单。
- 后端不需要做框题检测，少一个不稳定的 AI 步骤；只需一次多题文本提取。
- 当前阶段明确不做附图，避免生成题依赖不存在的图片。

### 负面/代价

- 用户需要自己裁剪图片；裁剪交互要做，但比 bbox 调整简单。
- 多题提取对模型结构化输出要求更高；需要严格的 JSON schema 和逐条校验。
- 多题条目增加前端状态：提取中、待确认、逐条编辑、选中、生成中。
- 多选生成会产生多个任务/多次 AI 调用，需要限制数量（P0 ≤3）并做成本控制。
- 含图题只能提取文字，图形信息会丢失；需要在 UI 明确提示。

## 4. 备选方案

| 方案 | 优点 | 缺点 | 为什么没选 |
|---|---|---|---|
| 原 AI 框题 + 用户调整 bbox | 可处理整页多题 | 框题不稳定、交互复杂、后端要多一步检测 | 用户反馈改为文本提取 |
| 整图直接识图，不裁剪 | 最简单 | 无关内容多、多题混在一起、识别质量差 | 上传裁剪更可控 |
| 只识别单题 | 实现简单 | 多题图要重复上传，体验差 | 多题条目更符合错题本场景 |
| 当前阶段同时提取附图 | 信息完整 | 附图识别/生成成本高，25 天不可控 | 明确延后 |

## 5. 接口与数据影响（摘要）

详细契约见 `docs/agent/05-architecture.md`（现 v0.6.3；本 ADR 只记决策，字段一律以 05 为准）。

- `POST /uploads/images`：接收裁剪后的图片；服务端校验/压缩/去 EXIF，返回 `image_path`。
- `POST /questions/from-image`：
  - 请求 `{image_path}`；
  - 返回 `{questions: [{index, content_md, question_type, options?, blanks?, has_figure, warnings?}], warnings?}`；
  - 不再返回 `candidates`、`bbox`、`confidence`。
- 用户确认后，前端对每道题调用 `POST /questions`（或后续批量端点）；每道题独立入队 analysis。
- 分析任务返回 `answer_md`、`explanation_md`、知识点、错误原因；用户确认后即可看到答案/解析。
- 生成：用户选中 1–3 道题，前端对每个 `question_id` 调用 `POST /questions/{id}/generate`；每个题目一个 `generation_task`。
- 数据模型：`questions.crop_box` 仅表示用户裁剪（可选）；`detection_confidence` 不再使用，建议移除；`image_path` 存裁剪后图片。

**落地后的两处补充（2026-11-06，实现时补，不改本 ADR 的决策）**：

- 条目多出 `subject` / `chapter` / `difficulty` 三个**初判**（FE-026 的预填与徽章要用）。它们只描述"图上有依据"的信息，
  正式值仍以用户确认 + analysis 为准，所以不构成第二真源。请求带了 `subject` 时后端逐条覆写，不用模型猜的值。
- `options?` / `blanks?` 的**可选性是承重的**：识图只保证文字，结构不自洽的条目整条降级成纯文本返回，
  不把半套结构交给用户（详见 §6 的复审记录与 05 §6.8）。

### 6.1 复审记录（2026-11-07）：结构化成功率触发

**数据**：三张实拍（复习题六 / 习题 7.1 / 密页横拍）共 14 个条目，按"能不能原样过严格入库校验"算，
12/14 = **86% < 90%**，条件成立。失败的 2 条都来自密页那张的填空题：图上 2 个空位只读出 1 个答案。

**预案的两条都没采用**，理由是它们治的不是这个病：

- 「降级为单题提取」改的是**一次看几题**，而失败原因是**答案根本不在图页上**（教材页不印答案）。
  一次只认一题，空位答案照样是空的。
- 「逐题重试」改的是**重试次数**，而模型第二次给的还是同一个空答案——重试只增加延迟和成本。

**实际处置**：识图的产物从"结构完整的题"收回成**"文本题目条目"**——结构不自洽的条目整条降级成纯文本
（`question_type=solve`、`options`/`blanks` 清空）+ `incomplete=true` + 一句"已按文本题返回，需要选择题/填空题请在编辑器里补结构"。
这不违背本 ADR：§2 决策的原文就是「AI 提取图片中的**题目文本**」，§5 的出参也把 `options`/`blanks` 写成了**可选**；
结构化本来就是 FE-020 三题型编辑器的活，不是识图的。原方案把它们当成"一般会有的附加字段"，实测证明是"常常残缺的字段"，
那就按可选来交付，别对用户假装结构化成功了。

**换口径后的数**：文字到手 14/14（这才是识图该有的成功率），模型报成选择/填空的 6 条里 4 条结构自洽、原样保住，2 条降级。
复现脚本 `_scratch/check_text_first.py`（三张实拍，同 prompt 重跑）。

**留下的问题（不在本 ADR 范围内解决）**：填空题在教材页**永远**会降级。真要保住结构，得等 analysis 读出答案后回填结构，
那是另一条链路（P1）；演示版的口径是"文字给你，题型你点一下"。
